Applies when NOTES.md says `stage: stakeholder`, or when the author brings feedback on the document from someone else (a stakeholder), at any stage. This stage turns that feedback into changes to the document. You first answer each point of the feedback, and the author answers your questions and chooses one of two paths. On the apply-and-mark path, you apply the agreed changes, and the author checks them all in one marked copy of the document. On the proposal path, the author decides each change before it is applied.

1. **Save the feedback.** If the stage is not `stakeholder` yet, set `return_stage` to the current stage (`finish` when the stage is `done`), so that the work goes back to it when the round closes, and set `stage: stakeholder`. If the feedback or a short name for the stakeholder (for example `legal` or `cfo`) is still missing: **Stop.** Set `waiting_for: "the stakeholder feedback"` in NOTES.md, ask for what is missing, and end the turn with the menu. If the author says that no feedback is coming, set `stage` to `return_stage` (or to `finish` when it is empty), clear `return_stage`, and go on with that stage.

   With the feedback and the name in hand, increase `round` by one and, in the same step, create the round folder reviews/r<n>-<stakeholder>/; its name is the round ID. Save the feedback verbatim to feedback/<yyyy-mm-dd>-<round-id>.md before you work with it, keeping any part in another language as it is, because the proposals quote it and the finish stage checks the document against it.

2. **Discuss the points.** Split the feedback into numbered points. For each one, say in chat whether you agree or disagree and why, with the facts it rests on checked against the sources or official documentation and cited (file:line, or a link), and what it would change in the document. Name any recorded decision that a point would reopen (D-<n>), because only the author can reopen it. End with numbered questions for what the author must decide. Write the same list to reviews/<round-id>/discussion.md, because the author's answers refer to its numbers and a resumed session needs them.

   At the end of the same message, unless the author already named a path, describe both paths in one line each, so that the author knows the choice exists (apply-and-mark: you apply the agreed changes and the author checks one marked copy; proposals: the author accepts or rejects each change before it is applied), and recommend one with a one-line reason:
   - apply-and-mark when the author is likely to agree with the points as you answered them, because the discussion then settles the substance, and a round with many changes is too much to decide one change at a time;
   - proposals when the author is likely to disagree with your view on several points, such as points that reopen a recorded decision, or when the author wants to decide change by change, because each change then waits for the author's yes before it reaches the document.

   **Stop.** Set `waiting_for: "answers on the points of the <round-id> feedback and the choice of path"`, ask the author to answer and to choose the path, and end the turn with the menu.

   When the author's answers name the path, or the author's first message already named it, follow it. When the author's answers disagree with your view on many points, or the author wants to decide change by change, take the proposal path. Otherwise follow your recommendation.

## Apply-and-mark path

3. **Apply the agreed changes.** Record each decision as a D-n line, `D-<n> (<date>, <stakeholder> feedback): …`, including each point the author declined, with the reason, so that later rounds do not raise it again. When a point reopens a recorded decision, end the new line with "Replaces D-<n>." and append "Replaced by D-<m>." to the old line. Then run `python3 <skill>/scripts/proposals.py snapshot reviews/<round-id> --doc <document>`, from the folder that references/proposals.md names. It copies the document into the round folder's base/, so that the marked copy can show every change against the text as it was before the round. Then apply every agreed change to the document, following references/drafting.md and the human-writing skill. On a resumed session, skip what is already done: the D-n lines already recorded for this round, and the snapshot when base/ exists.

4. **Show the changes.** Run `python3 <skill>/scripts/proposals.py changes reviews/<round-id> --doc <document>`, and give the path of the changes.html it writes. The page is a read-only copy of the changed files with new text in yellow, removed text struck through and an ID such as C-12 on each change for the author to quote. A change keeps its ID when you run `changes` again, so the author can name a change from an earlier page. The page shows Markdown files only, so list any change to another file, such as a navigation file, separately. Under the link, list separately and number every decision that you made while applying the changes and that the author did not state, headed "Please check these", and record each one as a D-n line as well. The author agreed to the points, but not to the way you applied them, and this list shows where you had to choose.

   **Stop.** Set `waiting_for: "the author's check of the <round-id> changes"`. Ask the author to read the marked copy and say OK, or to name the changes to redo by their IDs (C-<n>), and ask whether another round of feedback follows. End the turn with the menu.

5. **Redo and close.** Redo the changes the author named. When a redo changes a recorded decision, record the new decision as in step 3, with "Replaces D-<n>." on the new line and "Replaced by D-<m>." on the old one. Run `changes` again and stop again as in step 4, until the author says OK. Keep base/ until then, because each run of `changes` compares against it.

   When the author says OK, delete changes.html, changes-ids.json and base/ from the round folder, so that no outdated copy of the document is left to be mistaken for the current one. Run `python3 <skill>/scripts/proposals.py lint --notes NOTES.md <document>` and fix what it reports, as the Lint rule in SKILL.md describes. Add the Rounds line. If another round of feedback follows, stay in `stage: stakeholder`; otherwise set `stage` to `return_stage` and clear `return_stage`.

## Proposal path

3. **Write proposals.json** in reviews/<round-id>/, following references/proposals.md, with `kind: stakeholder`, `lens: stakeholder` and `quote` holding the point's words. On this path every point the author agreed to becomes a proposal, because only accepted proposals are applied. Take each proposal's why and sources from the discussion rather than splitting the feedback again. A point that reopens a recorded decision becomes a decision proposal. A point the author declined needs no proposal; record it as a D-n line with the reason, as on the other path. A change that touches many places can be one proposal with `manual: true` that lists every place. The old and new text of each proposal show the author how the document reads now and how it will read. Run `python3 <skill>/scripts/proposals.py check reviews/<round-id>` and fix every problem it reports.

4. **Present the round** the way stages/review.md step 6 describes: a numbered list in chat for about 15 proposals or fewer, otherwise the review page.

   **Stop.** Set `waiting_for: "decisions on the <round-id> proposals"`, ask the author to review and say when they are done, and end the turn with the menu.

5. **Apply the decisions** the way stages/review.md step 7 describes, with `<stakeholder> feedback` in place of `author` in the D-n lines.

6. **Confirm.** Show a short summary of what changed. **Stop.** Set `waiting_for: "confirmation of the <round-id> changes"`, ask the author to confirm and whether another round of feedback follows, and end the turn with the menu. When the author confirms: if another round follows, stay in `stage: stakeholder`; otherwise set `stage` to `return_stage` and clear `return_stage`.

**Exit:** the feedback file exists; NOTES.md has a D-n line for each decision, each declined point and each rejected proposal, and a Rounds line for this round; `stage` is `stakeholder` when another round follows, and otherwise the stage the round interrupted, with `return_stage` cleared. On the apply-and-mark path, the author said OK to the marked copy, and the round folder holds no changes.html, changes-ids.json or base/. On the proposal path, no proposal in the round has status `discuss`, and every accepted proposal is applied.
